# FyAgent v0.3.1 candidate (unpublished)

> [!IMPORTANT]
> **This is an unpublished candidate and preflight contract, not evidence of a
> v0.3.1 Release.** The existing annotated `v0.3.1` tag points to a different
> historical SHA and this task must not move or reuse it. The current work is
> therefore not the formal source for that tag and cannot publish or close a
> formal release under it. Only a future, independent version/tag decision can
> establish a publishable formal source. The currently allowed remote check is
> a same-SHA, non-publishing preflight after successful required push CI.

> [!WARNING]
> **Windows signing is evidence-driven, not assumed.** A formal release may use
> verified Authenticode signing when the complete signer configuration is
> available. When it is not configured, both Windows installers must prove
> `NotSigned`, and the Release must disclose that state. Partial configuration,
> invalid signatures, publisher/certificate drift, missing timestamps in signed
> mode, or different signing modes between architectures block publication. The
> workflow appends the exact per-architecture signing table to these notes from
> the verified `signing-status.json`; inspect that table before installing.

## Highlights

- **The Windows candidate contract uses NSIS:** the prospective Windows assets
  are per-machine x64 and ARM64 setup executables, built and packaged on
  matching native GitHub-hosted runners. MSI, WiX, and Portable ZIP are not
  v0.3.1 release formats. Setup and uninstaller use the canonical FyAgent icon.
- **Standard NSIS installation-directory behavior:** graphical and silent
  `/D=` installs do not pass through a FyAgent-owned absolute/fixed/local/UNC/
  reparse/drive-type, ACL-owner, or protected-folder admission gate. Standard
  NSIS/Windows parsing still applies, and an actual filesystem or registration
  write can still fail. FyAgent no longer creates, repairs, or requires a
  `%ProgramData%\FyAgent\runtime`; only known legacy names are considered for
  best-effort, non-recursive cleanup, and unknown/inaccessible content is
  preserved.
- **Shell-user-bound Codex lifecycle on Windows:** ordinary Codex Desktop
  discovery, installation/update, post-verification, restart, and launch now
  carry one immutable Explorer Shell-user context. Elevated Bob can therefore
  serve Alice's Explorer session without selecting Bob's profile. Package
  inventory uses Alice's SID explicitly with `PackageTypes.Main`; zero, one,
  or multiple trusted Stable packages map to not installed, installed, or
  fail-closed ambiguity without broadening to another user.
- **Narrow current-user Codex helper:** the Windows bundle includes a separate
  `asInvoker` helper with no Tauri runtime. Explorer launches only its fixed
  current-user MSIX action. The elevated parent pins the verified install-root
  package and seals one immutable operation copy below
  `FyAgent.PackageBridge-{96F39D37-0F42-486F-8C86-3631C12171C5}\v1` in Windows
  CommonApplicationData. The fixed root ACL is stable across users and grants
  Authenticated Users only execute/traverse, read-attributes, `READ_CONTROL`, and
  synchronize rights—never list or mutate; each operation grants only the
  exact Explorer user the minimum read/traverse access and denies namespace
  mutation. The authenticated order is `Hello` →
  bridge control → verified `Started` identity → parent admission, after which
  the helper constructs only the protected local file URI and calls current-user
  `PackageManager.AddPackageByUriAsync`. Arbitrary paths/URIs, HTTP/network/
  Temp/install-root fallbacks, and the retired all-users, headless/runas,
  control/job-file, Stage, and Provision surfaces are absent. The application
  cleans a bridge operation only after a true WinRT terminal result, matching
  terminal frame, and clean pipe close; ambiguous state leaves an immutable
  known-only orphan for a later elevated application run. NSIS never cleans or
  repairs PackageBridge.
  Renderer exit/restart no longer has a raw Tauri process capability: guarded
  commands atomically claim the same slot as installer start, so a running or
  quarantined job prevents a new job or normal exit.
- **Standalone locked local tooling:** contributors use
  `mise trust` → `mise run bootstrap` → `mise run system:check` →
  `mise run dev`, with `mise run check` as the full pre-commit gate. Upstream
  Trellis files remain optional assistance and history; repository overlay,
  reconcile/verify wrappers, and bootstrap prompt injection are removed.
- **Domain-aware collaboration CI with full development-branch gates:** pull
  requests and merge queues run the affected contract/frontend/desktop/backend/
  Windows-native/docs domains, unknown paths fail closed, and
  `dev/laiyongjie` pushes always run the complete `CI / Required` graph.
- **Exact-SHA development-branch preflight:** preflight never publishes. The
  current task may run it only for the exact `dev/laiyongjie` push SHA after
  successful complete push CI. It runs matching native x64/ARM64 build,
  package, and sealing jobs against the immutable candidate but does not run
  the optional setup/uninstaller lifecycle diagnostic. The existing annotated
  `v0.3.1` tag identifies a different historical SHA, so this work is neither
  that tag's formal source nor eligible for formal publication under it.
- **Current documentation has a single authority model:** the versioned design
  packages under `docs/fyagent/dev/` were classified and removed. Current
  behavior now routes through code, executable contracts, and maintained
  responsibility-oriented development documents. Optional Trellis notes do
  not become a contribution, build, CI, or release prerequisite, while real
  protocol, schema, third-party API, and toolchain versions remain protected.

## Download and trust guidance

### Windows

Choose the NSIS setup executable matching the machine architecture:

```text
FyAgent-0.3.1-Windows-x64-setup.exe
FyAgent-0.3.1-Windows-arm64-setup.exe
```

Read the dynamically appended **Windows installer signing status** table. For a
signed row, require the reported Authenticode status, publisher, certificate,
and timestamp policy to match the published evidence. For a `NotSigned` row,
expect Windows SmartScreen to warn and do not treat the artifact as equivalent
to an Authenticode-signed installer. In either mode, verify SHA-256, source SHA,
and attestation. Do not disable SmartScreen, remove origin metadata, or weaken
organization-managed security policy.

### macOS

Choose the DMG or ZIP; both contain the Universal application:

```text
FyAgent-0.3.1-macOS.dmg
FyAgent-0.3.1-macOS.zip
```

The complete universal app is ad-hoc signed with no certificate identity, and
that signature is verified before packaging. It is **not signed with an Apple
Developer ID** and is **not notarized**; ad-hoc signing does not provide a
certificate-backed publisher identity or Apple trust. The ZIP and DMG contain
the same ad-hoc-signed app, while the **DMG container is unsigned**. After first
attempting to open FyAgent, use **System Settings → Privacy & Security → Open
Anyway** and confirm only after checking the Release evidence. Do not disable
Gatekeeper or remove quarantine metadata.

### Linux

Choose the exact architecture and package format required by the host:

```text
FyAgent-0.3.1-Linux-x86_64.AppImage
FyAgent-0.3.1-Linux-x86_64.deb
FyAgent-0.3.1-Linux-x86_64.rpm
FyAgent-0.3.1-Linux-arm64.AppImage
FyAgent-0.3.1-Linux-arm64.deb
FyAgent-0.3.1-Linux-arm64.rpm
```

Flatpak remains a local diagnostic conversion and is not a formal v0.3.1
installer.

```text
FyAgent-0.3.1-Linux-arm64.deb
FyAgent-0.3.1-Linux-arm64.rpm
```

It must also contain exactly these **4 evidence attachments**:

```text
download-manifest.json
build-metadata.json
signing-status.json
artifact-attestation.sigstore.json
```

That is **14 attachments total**. The attestation has exactly 13 subjects: the
ten installers plus `download-manifest.json`, `build-metadata.json`, and
`signing-status.json`. The copied Sigstore bundle is the fourteenth attachment
and does not attest itself. Missing, duplicate, renamed, empty, stale, or extra
attachments block publication.

## Compatibility and data boundary

v0.3.1 does not introduce a database-schema or user-data migration. Existing
provider, settings, skills, backup, `fyagent://v1/import`, and third-party `/v1`
contracts remain owned by their current implementation and active specs.

The Windows package format changes from MSI to NSIS. Uninstall removes only
installer-owned payloads, shortcuts, registration, the uninstaller, and empty
installer directories; it must preserve FyAgent databases, configuration,
OAuth state, backups, storage, user-profile sentinels, and unrelated files in a
custom installation directory. The repository retains an optional bounded
Windows lifecycle harness, but it is a manual diagnostic rather than a CI or
Release gate. Matching native x64 and ARM64 CI paths provide build, package,
manifest, icon, and signing/sealing evidence without executing setup or the
uninstaller.

## Candidate provenance and residual risk

The existing annotated `v0.3.1` tag points to a historical SHA that differs
from this candidate. This task explicitly may not move, delete, or reuse that
tag, so the current batch cannot be its formal source and cannot formally
publish or close v0.3.1. The only allowed release-workflow execution here is a
non-publishing preflight whose source exactly matches the live remote
`dev/laiyongjie` HEAD and a successful full push `CI / Required`. Formal
publication requires a future independent version/tag decision outside this
task.

The accepted residual risks remain visible:

- Official Trellis `0.6.14` Codex hooks are retained without FyAgent's former
  realpath containment, exact-source import binding, strict session/input
  checks, and breadcrumb escaping. This is an intentionally accepted security
  regression in prompt-assistance hooks, not an equivalent hardening migration.
- The current-user helper is not a protected process. Same-SID code injection
  or memory/handle manipulation remains within Alice's existing PackageManager
  authority; resisting it would require the excluded trusted broker/service.
  Normal UI, restart, setup, and uninstall paths preserve the source and bridge
  pins, but administrator force-kill, process crash, and OS shutdown are not
  durable terminal proof; they may leave a protected immutable bridge orphan.
- This delivery does not run HIL locally or in Actions for the local-file A1
  path. Its present evidence is limited to static contracts, scoped
  Windows-target compilation checks, and code/security review. Real Windows
  10/11, x64/ARM64, elevated-Bob/standard-Alice-Explorer-Shell, protected
  file-URI/PackageManager, effective ACL/mutation denial, and cleanup runtime
  behavior remain explicit unverified residual risks. Do not treat that
  evidence as a native-compatibility or native-runtime-verification claim. A2
  Stage/Register is not a shipped fallback; only future independent native
  validation plus an explicit, separately authorized decision may start its
  implementation and review. The minimum supported Windows version is
  unchanged.
- Setup never force-terminates FyAgent or its helper. Its final process lookup
  is a point-in-time safety check, not an atomic interlock against a new launch
  immediately before filesystem mutation.
- `windows-11-arm` is a public-preview GitHub-hosted runner; unavailability is
  a release blocker and is not replaced by cross-compilation.
- A verified `NotSigned` Windows release may trigger SmartScreen warnings;
  digest, source-SHA, and attestation evidence do not equal Authenticode trust.
- The macOS app has only an identity-free ad-hoc signature; the DMG container
  is unsigned, and neither is Developer ID signed or notarized. Gatekeeper may
  therefore require the supported Open Anyway flow.
- This release chain does not add branch protection, a ruleset, or Main
  Provenance. Repository write freeze during the release transaction is an
  operational prerequisite.

## Verification boundary

Local contract checks prove source, task, and workflow structure only. The
remote evidence allowed and required for this candidate task is limited to:

1. the unified work-commit push at the current remote development-branch HEAD;
2. successful complete `CI / Required` for that exact push SHA;
3. successful non-publishing preflight for the same SHA, including matching
   native Windows x64/ARM64 build, package, sealing, and exactly 14 verified
   preflight attachments.

Annotated-tag equality, a formal workflow, public Release/Latest state, and
post-publication verification are not completion steps for this task: the
existing tag mismatch makes them impossible without moving or reusing that tag.
They require a future independent version/tag decision. This document must not
be read as a claim that the current batch belongs to the existing `v0.3.1` tag,
or that v0.3.1 has been published or independently verified.
